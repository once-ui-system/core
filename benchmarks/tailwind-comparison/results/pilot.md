# Pilot results: Once UI vs Tailwind (PRELIMINARY)

> **PRELIMINARY. Not for public claims.** 3 of 12 tasks, n = 3, generated by Claude Code
> subagents rather than the pre-registered API protocol. Token figures mix exact Claude
> input counts with proxy-tokenizer output and code counts. Every number below is
> reproducible from `results/pilot/` with the scripts in `runner/`. The method is in
> [`../METHODOLOGY.md`](../METHODOLOGY.md), committed before generation started.

- **Date:** 2026-10-11. **Model:** `claude-sonnet-5-5`, recorded in every subagent transcript.
- **Once UI:** 2.1 release candidate, `d070802` on `claude/gifted-volta-armczp`. **shadcn/ui:** `c2a6784`.
- **Tasks:** 3 Pricing page, 6 Auth flow, 9 Data table page. That's every third task, a rule fixed in advance.
- **Arms:** A Once UI + harness · B Once UI from memory · C Tailwind v4 + shadcn/ui + its
  docs and agent skill · D Tailwind v4 from memory (+ lucide-react).
- **Runs:** 36 accepted (4 arms × 3 tasks × 3), after regenerating 4 voided runs (see "Protocol incidents").

## Headline numbers (A vs C, the pre-registered primary comparison)

Per-task medians over 3 runs. Reduction = 1 − A ÷ C, so a positive number means Once UI used less.

| Metric | Task 3 | Task 6 | Task 9 | Median of tasks (range) |
|---|---|---|---|---|
| Code tokens, page only, normalised (proxy o200k) | 24% | 51% | 40% | **40%** (24% to 51%) |
| Same, legacy-Claude proxy tokenizer | 26% | 52% | 41% | 41% (26% to 52%) |
| Code lines, normalised | 15% | 44% | 42% | 42% (15% to 44%) |
| Code bytes, normalised | 23% | 52% | 49% | 49% (23% to 52%) |
| Visible output tokens per run (proxy; excludes hidden thinking) | 7% | 38% | 26% | **26%** (7% to 38%) |
| **Total tokens per run** (exact input net of Claude Code overhead + proxy output) | −436% | −144% | −300% | **−300%** (A uses about 4× more) |

**What the pilot says:**

1. **Less code: consistent and sizeable.** With the harness, Once UI pages carried 24–51% fewer
   code tokens than the shadcn/ui pages, on 3 of 3 tasks, and the ratio barely moves between
   the two proxy tokenizers. shadcn/ui also copied **3.3k–7.6k tokens of component source**
   (median 407–919 normalised lines) into each project, on top of the page. Once UI keeps
   that in `node_modules`.
2. **Fewer output tokens: likely, but smaller.** The model generated 7–38% fewer visible tokens
   for A. Hidden thinking tokens are not visible in the pilot. The full run measures them exactly.
3. **Total tokens: the opposite.** A read a median of about 81k tokens of harness docs per run,
   and every later turn re-sends that context, so A's total tokens were about 3–4× C's. C read
   almost no docs: median 1 docs file per run, plus a few installed component sources. Under the
   pre-registered rules **no "fewer tokens" claim is possible today**. See the harness finding below.
4. **Quality gate (claim condition 5) currently fails.** Blinded medians: responsiveness A 3 vs C 4
   (C is the shadcn/ui arm). Part of that is a measurement artefact (see "Method changes"), but
   not all of it.

## Findings for the Once UI harness (not benchmark results)

- **`spec.json` dominates harness cost.** `ai/spec.json` (122 KB, about 37k tokens) was read
  14 times in 6 of the 9 arm-A runs: 89% of all harness tokens read (514k of 579k, proxy). `rules.compact.md`
  sends agents there for icon names ("take names from `spec.json`"). A small icon-name list
  (or putting icon names in `catalog.json`) could cut most of A's documentation cost without touching what the model sees for components.
- **`SegmentedControl`.** The model wrote `onToggle` twice with the harness, even though the
  slice and the gold example correctly show `onChange`. The prop type inherits the DOM
  `onToggle` (a `ToggleEvent` handler), so the mistake type-checks as a confusing mismatch
  instead of "unknown prop".
- The bootstrap files named in `AGENTS.md` cost about 12k tokens (proxy). shadcn's skill +
  `llms.txt` cost about 9k. The full docs corpora are similar (about 278k vs 300k).

## Protocol incidents (all logged; raw evidence in `work/` is session-local)

- **4 runs voided and regenerated.** During repair rounds, subagents patched their own output
  file with a shell `sed`/`python` call instead of re-writing it. No information came from
  outside the sandbox, but a shell patch would understate output tokens, so the
  pre-registered void rule was applied. The pilot repair prompt now restates "no shell commands".
- **3 render results voided (gate bugs, fixed before re-gating).** (a) Next.js `next/link`
  prefetches placeholder links like `/terms` in production. The resulting 404s were counted as
  console errors, penalising any page that uses `next/link`, which Once UI's `LayoutProvider`
  does for every link. Prefetch requests are now ignored. (b) The readiness probe treated an
  HTTP 500 as "server not up". (c) `networkidle` never settles on some pages, so the gate now
  waits for `load` plus 1.5 s.
- One subagent used `Edit` on its own output file. That's allowed: the file is still written by the model.
- Subagent transcripts record output usage as of the start of each stream, so **exact output
  tokens were not available** in the pilot. Output is measured as proxy tokens of everything
  the model generated (text + tool-call JSON). Thinking is redacted in transcripts and not counted.

## Method changes the pilot suggests (for sign-off before the full run)

> **Update 2026-10-11:** Lorant approved changes 3–6. They are implemented and logged in
> METHODOLOGY §11. Change 7 is moot: the `spec.json` and `SegmentedControl` fixes ship in
> 2.1.0 itself. The full run is on `2.1.0-rc.0`; see [`../RUN.md`](../RUN.md).

Already applied, because they are harness bugs or API constraints, not judgement calls (logged
in METHODOLOGY §11):

1. Render gate: ignore Next.js router prefetches, probe readiness on any HTTP response, wait on `load` + 1.5 s.
2. `claude-sonnet-5-5` rejects `thinking: {type: "disabled"}` and non-default sampling
   parameters. The full run uses `thinking: {type: "between_tools"}` (the documented thinking-off
   mode), effort `high`, and the default temperature.

Proposed, not applied (each changes what is measured, so it needs sign-off):

3. **Interaction screenshots.** Static screenshots cannot see dialogs, OTP steps, hovers or sorting.
   On task 6 most pages show only a "Sign in" button, and completeness scores of 1–2 measure the
   screenshot, not the page. Proposal: one scripted state per task, written before the run and
   identical for all arms (e.g. click the first button whose name matches /sign in|log in/,
   screenshot the dialog).
4. **Rater instructions for horizontal scroll.** Every arm's phone table was called "clipped".
   A horizontally scrollable table is the correct responsive pattern. Proposal: tell the rater
   that regions may scroll horizontally, or capture each scroll container's full width.
5. **Report cache-aware cost as a secondary metric.** Real agents cache the re-sent prefix.
   "Total tokens" (pre-registered, uncached) penalises multi-turn doc reading at full price. Add
   "cost at list prices with prompt caching" next to it. It would not replace the pre-registered metric.
6. **n = 5 instead of 3.** The run is cheap (below), and the polish/responsiveness gaps are within one point.
7. **Harness revision is a separate arm, not a fix.** If the `spec.json` finding is addressed in
   2.1.x, measure it as A′ alongside A, so the claim is about the shipped harness.

## How confident could the full run's claims be?

- **"Less code" (page tokens), A vs C:** likely to clear the statistical bar. The pilot effect
  is 24–51%, all three tasks agree, and both tokenizers agree. The risks are the quality
  condition (responsiveness) and tasks 1, 5 and 8, which may inflate the effect (hence the
  pre-registered sensitivity analysis). With condition 5 as written, the claim currently fails
  on responsiveness.
- **"Fewer output tokens":** plausible but smaller (7–38%). Hidden thinking could narrow or
  widen it. It needs the exact API run.
- **"Fewer tokens" (total):** not supported. The pilot shows the reverse by about 4×. Only a
  harness change (e.g. no `spec.json` reads) could change that, and it would have to be measured
  on the shipped version.

## Cost and time of the full run

Per-run averages from the pilot, excluding Claude Code's overhead: about 39k input and 5k output
tokens per run (arm A about 110k input). At `claude-sonnet-5-5` list prices ($2 / $10 per M
tokens, no caching, as pre-registered):

| | n = 3 (144 runs) | n = 5 (240 runs) |
|---|---|---|
| Generation (incl. repairs; tasks 1–12 assumed 1.5× the pilot tasks) | ≈ $30 | ≈ $50 |
| Blinded rater calls (3 images each) | ≈ $2 | ≈ $4 |
| `count_tokens` (code, context) | free | free |
| **Total, with 2× safety margin** | **≈ $65** | **≈ $110** |
| Wall-clock (4 arms in parallel; gates about 30–60 s per attempt) | ≈ 2 h | ≈ 3–4 h |

The planned re-run against the published 2.1.0 costs the same again. A replication on
`claude-opus-5-5` would cost about 2×.
