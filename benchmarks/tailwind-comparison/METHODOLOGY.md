# Once UI vs Tailwind: tokens and code to build the same UI (pre-registered method)

**Status:** pre-registered. This file was committed before any generation ran. The git
history is the record: any later change to this file, `config.json` or `prompts/` must be
logged in §11 with its reason and date. A change made after the full run starts makes
that run exploratory, not confirmatory.

**Question.** For the same UI tasks, the same model and the same instructions, how many
AI tokens does it take, and how much code does the model write, to get a working page
with Once UI compared with Tailwind CSS (with and without shadcn/ui)?

**Goal.** Numbers that can be stated publicly and defended, e.g. "x% less code",
"y% fewer tokens". So: one method, fixed in advance; every number traceable to a raw
output in `results/`; the result gets reported whichever arm it favours.

---

## 1. Arms

Every arm is a Next.js app on identical versions (`config.json` → `versions`: Next
16.2.12, React 19.2.8, TypeScript 6.0.3 strict, Node 22). Scaffolds live in `arms/`
and are committed with their lockfiles.

| Arm | Stack | Context the model can read | Scaffold |
|---|---|---|---|
| **A** `once-harness` | Once UI 2.1 (`@once-ui-system/core`, release-candidate tarball, see §1.1) | The harness exactly as shipped in the package: `AGENTS.md` + `ai/**` (rules, catalog, task bundles, component slices, gold examples, block references), **minus** `ai/eval-tasks.md` | `arms/once`: standard provider stack (Theme, Layout (next), DataTheme, Toast, Icon) and the two package stylesheets, mirroring the official starter |
| **B** `once-memory` | Once UI 2.1 | Nothing but the project's own files | same as A |
| **C** `shadcn-docs` | Tailwind CSS v4.3.3 + shadcn/ui (new-york-v4, Radix, neutral) + lucide-react | shadcn's strongest official AI context, as a local copy: the official **agent skill** (`skills/shadcn`, rules included), **`llms.txt`**, per-component docs, the example source behind every docs preview, and the official **blocks** | `arms/shadcn`: the output of `shadcn init` (taken from shadcn's own `next-app-init` fixture), with **every** registry component pre-installed under `components/ui`, and sonner's `<Toaster />` mounted |
| **D** `tailwind-memory` | Tailwind CSS v4.3.3 + lucide-react, no component library | Nothing but the project's own files | `arms/tailwind`: `@import "tailwindcss"` only |

All arms can read their own project files (`project/`: layout, providers, global CSS,
`package.json`, and, for C, all of `components/ui`). No arm can read `node_modules`.
A and C differ from B and D only in having a `docs/` folder. The pairs are symmetric:
**docs vs docs** (A–C) and **memory vs memory** (B–D).

### 1.2 Choices that favour the competitor, made on purpose

Where a choice had to be made, it went against Once UI, so the headline can't be
blamed on the setup:

- C gets shadcn's **agent skill** as well as `llms.txt` and the docs: that's the closest
  equivalent to Once UI's harness, not a weaker stand-in.
- C has **every component pre-installed**. In real use the model would run
  `npx shadcn add …`, which costs turns and tokens that are not counted here.
- C can read the installed component **source** (`components/ui/*.tsx`).
- D gets **lucide-react**. Without an icon library, D would have to inline SVG paths,
  which would inflate its code.
- A's context excludes `ai/eval-tasks.md`, which ships in the package but names the
  expected Once UI components for each task in this suite.
- Tailwind class strings and Once UI props both count as code (§4.3). Nothing gets
  discounted for either stack.

## 2. Model and settings

- **Model:** `claude-sonnet-5-5`, the same for every arm, task and run.
- **Settings** (`config.json` → `generation`): `max_tokens` 16,000, thinking
  `{type: "between_tools"}` (Sonnet 5.5's thinking-off mode), effort `high`, default
  temperature, no prompt caching (so `input_tokens` is the full input). *Amended 2026-10-11,
  before any full-run generation: the original "temperature 1.0, thinking disabled" is rejected
  by `claude-sonnet-5-5` with a 400 (§11).*
- **Tools:** every arm gets the same two tools, `list_dir(path)` and
  `read_file(path)`, rooted at that arm's sandbox (`project/` and, for A and C,
  `docs/`). Reads over 150,000 characters are truncated, with a marker. Each attempt
  can make at most 40 tool calls. Tool definitions are identical across arms, so
  their token cost is too.
- **One conversation per run.** Repair rounds (§3.3) continue the same conversation.

## 3. Tasks, prompt and gates

### 3.1 Tasks

The task set is the 12-task suite in `packages/core/ai/eval-tasks.md`. It predates this
comparison (first committed 2026-06-12; first run in `docs/evals/2026-08-26-baseline.md`).
It was written to test the Once UI harness, not to compare stacks, which cuts both ways
(see §8).

**Neutralisation.** The suite's descriptions are aimed at Once UI. Each task's "Tests:"
clause names Once UI components. The prompt each arm sees keeps the title and
description, drops the "Tests:" clause, and replaces backticked Once UI component names
with plain nouns. Only tasks 10 and 11 needed a replacement (`UserMenu`/`HoverCard` →
"a user menu or hover card", `Timeline` → "a timeline"). The exact text is in
`prompts/tasks.json`, with each original alongside.

**Pilot subset:** tasks 3, 6 and 9 (every third task, a mechanical rule). The pilot
results are not part of the confirmatory run.

### 3.2 Prompt

`prompts/system.md` + `prompts/user.md`, identical for every arm except the one
`{{STACK}}` sentence from `prompts/stacks.json`. The prompt asks for exactly one file,
`app/page.tsx`, with inline placeholder content and no network assets (no remote
images or fonts, which would fail the build or render in some arms and not others).
It also asks for a responsive, accessible page, returned as one fenced `tsx` block.
The page is the last fenced code block of the final reply.

### 3.3 Acceptance gates (in order) and repair loop

Each attempt's page is copied into the arm's scaffold as `app/page.tsx` and run through
these gates:

1. **extract:** the reply contains a fenced code block.
2. **typecheck:** `tsc --noEmit` (strict) on the whole scaffold passes.
3. **build:** `next build` passes.
4. **render:** `next start`, then headless Chromium loads `/` at 375, 768 and 1440 px.
   It passes when there is no `console.error`, no uncaught page error and no failed
   same-origin request (a `/favicon.ico` 404 is the only ignored message), and the
   page shows content (body text ≥ 40 characters and document height ≥ 200 px, so an
   empty page can't pass).

**Recorded, not gated:** axe-core violations (rule count, node count, serious/critical
count) at 1440 px; full-page screenshots at all three widths (JPEG q70, capped at
6000 px tall); Once UI's own `validate-ai-code` issues, for arms A and B only, as a
secondary harness-quality signal.

**Repair loop:** when an attempt fails a gate, the model gets the first failing gate's
output (`prompts/repair.md`, clipped to 4,000 characters) and returns a corrected file.
It gets at most **3 repair rounds**, so 4 attempts in total. A run is **accepted** if an
attempt passes every gate, and **failed** otherwise. Tokens and code are counted up to
and including the first passing attempt, so repair rounds count. Smaller code that
doesn't work is not a win: failed runs don't count towards code-size medians, they
count against the pass rate, and their tokens appear in cost-per-accepted-result (§4.1).

Infrastructure failures (API errors, a crashed browser) void the attempt. It is re-run
and logged in the run's `run.json`. Model output is never voided.

## 4. Metrics

### 4.1 Tokens (exact Claude counts)

Taken from the API `usage` fields of every call in the run, up to the accepted attempt:

- **Output tokens** = Σ `output_tokens`. This includes tool-call turns and repair rounds.
  **Headline token metric.**
- **Total tokens** = Σ (`input_tokens` + `output_tokens`). This includes every
  documentation read, because each tool result is re-sent as input on later turns.
- **Cost per accepted result** = total tokens of all runs for a task and arm, including
  failed runs, ÷ accepted runs.

### 4.1a Cache-aware cost (secondary; added 2026-10-11, §11)

Real agents cache the re-sent prefix of a conversation, and the uncached "total tokens"
above charges every re-read of documentation at full price. Next to it, and never instead
of it, the report gives each run's **cost at list prices** two ways: uncached, and with
prefix caching assumed. With caching, each call's input up to the previous call's input +
output is priced as a cache read and the rest as a cache write; output is unchanged.
Prices are in `config.json` → `pricing_usd_per_mtok`. No claim is made from this metric.

### 4.2 Context tokens (cost of each arm's harness or docs)

- **Corpus:** exact token count (`count_tokens`) of every readable docs file, summed.
- **Bootstrap:** the files the stack sentence and the entry file direct the model to
  load first. For A: `AGENTS.md` → `ai/manifest.json`, `ai/rules.compact.md`,
  `ai/catalog.json`. For C: `README.md` → `skill/SKILL.md`, `llms.txt`.
- **Consumed:** per run, the tokens of every tool result the model actually received.

### 4.3 Generated code size

Measured on the accepted `app/page.tsx`, after normalisation: comments stripped (with the
TypeScript printer), then formatted with Prettier 3.9.10 using its defaults. That way
formatting style and comment chattiness don't count for or against any arm. Raw
(un-normalised) figures are reported too.

- **Lines** (non-blank), **characters**, **UTF-8 bytes**, and **tokens of the code alone**
  (`count_tokens` of the code as a single user message, minus the count for a one-character
  message).
- **Headline code metric: code tokens.** Lines are reported, but line counts depend on
  formatting more than tokens do.
- Tailwind class strings and Once UI props are both code, and both count.
- **Vendored code (C only).** shadcn copies component source into the app. The headline
  counts only the model-written page. Separately, for each accepted C result, the report
  counts the transitive closure of `@/components/ui/*`, `@/lib/*` and `@/hooks/*`
  imports from the page (normalised the same way) as **"code you own and maintain"**.
- **Scaffold constants** (layout, providers, global CSS) are reported once per arm and
  kept out of the per-task figures.

### 4.4 Reliability

- Number of repair rounds to acceptance (0–3).
- **Gate pass rate**: accepted runs ÷ runs, with the first-attempt pass rate shown
  separately.

### 4.5 Blinded quality rating

Screenshots are relabelled with random IDs. The mapping comes from a seeded shuffle and
is stored separately, then committed once rating is done. The rater scores each result
1–5 on the eval-tasks.md judgment rubric, with the Once UI-specific wording made
neutral:

| eval-tasks.md axis | Neutral wording used here |
|---|---|
| Proportionality ("look like real Once UI") | **Visual polish:** consistent spacing rhythm, type scale and surface hierarchy |
| Component appropriateness | **Task completeness:** every element the task asks for is present and plausible |
| Responsiveness | **Responsiveness:** layout adapts sensibly across the three widths |
| Restraint | **Restraint:** effects and decoration support the content rather than dominate it |

**Interaction screenshots (added 2026-10-11, §11).** A static screenshot cannot show a
dialog, an OTP step, a hover state or a sorted table. Each task has one scripted
interaction in `prompts/interactions.json`, written before the full run and identical
for every arm: a click or hover on the first control found by accessible role and name
(or plain semantic HTML), e.g. "the first button named Sign in". After the gate's own
checks, the gate performs it at phone and desktop width and takes a viewport screenshot.
A missing control is recorded and told to the rater. Errors during the interaction are
recorded, not gated.

**Rater:** a separate `claude-sonnet-5-5` call per result (`runner/rate-api.mjs`), with
images only (three widths, plus the interaction screenshots) and the task text, prompt in
`prompts/rater.md`. The prompt tells the rater that content scrolling sideways inside its
own container, like a wide table on a phone, is acceptable and isn't clipping (added
2026-10-11). Sampling is the API default: the pre-registered temperature 0 is rejected by
`claude-sonnet-5-5` (§11). Stack
fingerprints such as default fonts or colour palettes can't be fully hidden, which is
a known limit of the blinding. A blinded human pass over a random 25% sample is
recommended. If one is done, it gets reported next to the model rater, never
instead of it.

## 5. Runs and statistics

- **n = 5 runs per task per arm** (12 × 4 × 5 = 240 runs; raised from 3 on 2026-10-11, §11).
  n is fixed in `config.json` before the full run starts and can't be raised partway through.
  **The 2.1.0 claim run is trimmed** (2026-10-15, §11): arms A and C only, **n = 3**
  (12 × 2 × 3 = 72 runs), because of budget. The claim conditions in §5.1 are unchanged;
  the §5.2 wording then says "3 runs per task". Arms B and D are not run on 2.1.0, so the
  secondary comparisons are reported from rc.0 only and stay internal.
- Per task and arm: the **median** and **IQR** (type-7 quantiles) of each metric over
  accepted runs.
- Per task and arm pair (X vs Y), for tasks where both have ≥ 1 accepted run:
  **reduction** r = 1 − median_X ÷ median_Y.
- **Across tasks:** the **median of the per-task reductions**, the **range** (min–max),
  the IQR, the number of tasks with r > 0, and a **95% bootstrap CI** of the median
  (10,000 resamples over tasks, seed 20261011).
- **Per-task tables** for every metric and arm are always published.
- **Primary comparison:** A vs C. Secondary: A–D, B–C, B–D, A–B (harness effect),
  C–D. Only the primary comparison can support a headline claim. Secondary results are
  reported but not headlined.
- **Sensitivity analysis:** the A–C headline is recomputed without tasks 1, 5 and 8.
  Their original "Tests:" clauses name Once UI-only effect components (`CountFx`,
  `LetterFx`/`Background`, `CelebrationFx`), so they are the most likely to favour
  Once UI. Both numbers are published.

### 5.1 When a claim may be made (decided now)

A public "X% fewer / less" claim for A vs C on a metric is allowed only if **all** of
these hold:

1. The lower bound of the 95% bootstrap CI of the median reduction is > 0.
2. r > 0 on at least 9 of the compared tasks.
3. The reduction is still > 0 in the sensitivity analysis (tasks 1, 5 and 8 excluded).
4. A's gate pass rate is no more than 10 percentage points below C's.
5. A's median blinded rating is no more than 0.5 below C's on every axis.

If any condition fails, no headline claim is made for that metric. The result is still
published, in the same format.

### 5.2 Exact claim wording (fill in the numbers, change nothing else)

> **Output tokens:** "Across 12 UI tasks, `claude-sonnet-5-5` used a median **X%** fewer
> output tokens to build a working page with Once UI 2.1 and its AI harness than with
> Tailwind CSS v4 + shadcn/ui and its docs (per-task range **a%** to **b%**, 5 runs per
> task; every counted page type-checks, builds and renders without console errors)."

> **Code:** "…and wrote a median **X%** less code: tokens of the formatted page,
> comments removed (per-task range **a%** to **b%**). shadcn/ui additionally copied a
> median **V** lines of component source into each project."

> **Total tokens:** "Counting the cost of reading each stack's documentation, the median
> total-token reduction was **X%** (range **a%** to **b%**)."

Rules: X is rounded **down** to a whole percent. When the range includes negative
values, say so, e.g. "range −8% to 61%". Always name the model, the versions, the number
of tasks and runs, and link to `results/`. Never round "median" off to "on average".
Lorant approves every public claim before it is used.

## 6. Token counting and API access

Exact counts come from the API `usage` fields (generation) and the `count_tokens`
endpoint (code, context). These need an `ANTHROPIC_API_KEY`.

**Status at pre-registration (2026-10-11):** the benchmark environment has no
`ANTHROPIC_API_KEY` (checked by variable name only; no secret values are printed or
stored). The full run can't execute until a key with a budget is provided. Until then:

- `runner/generate-api.mjs` implements the exact protocol above and refuses to run
  without a key.
- The **pilot** uses the fallback in §7. Code and context figures there use **clearly
  labelled proxy tokenizers** (OpenAI `o200k_base` and Anthropic's legacy pre-Claude-3
  tokenizer, both reported). Neither is a current Claude tokenizer.

## 7. Pilot protocol (fallback, a documented deviation)

Purpose: test the tooling and the method, and estimate variance and cost. The pilot
can't support public claims.

- **Tasks** 3, 6 and 9 × arms A–D × n = 3 = 36 runs, same gates and repair cap.
- **Generation** by Claude Code subagents in a single session, one fresh subagent per
  run, `model: sonnet` (the transcripts record `claude-sonnet-5-5`). Each subagent
  gets the identical `user.md` prompt for its arm. Two short preamble lines (the same
  for every arm except the sandbox path) tell it where its sandbox is and to write the
  file to a given output path rather than replying with it. Repair rounds go to the
  **same** subagent (conversation continued).
- **Exact Claude token counts** come from the subagent transcripts (`usage` per API
  call) for **input**. *Found during the pilot:* transcripts record output usage as of the
  start of each stream, so output is measured as proxy tokens of everything the model
  generated (text and tool-call JSON). Thinking is redacted in transcripts and is not counted. **Input/total tokens** also include Claude Code's own system prompt, tool
  schemas and repository instructions (≈ 53.6k tokens on the first call, re-read
  from cache on every later call). That overhead is the same for every arm but grows
  with the number of turns, so pilot totals overstate the docs arms' cost compared
  with the bare API protocol. They're reported with the measured empty-agent
  baseline subtracted, and labelled.
- **Deviations from §2:** thinking and temperature are Claude Code's defaults, not
  pinned. Tools are Claude Code's Read/Glob/Grep (restricted by instruction to the
  sandbox), not `list_dir`/`read_file`.
- **Contamination check:** the session's repository instructions (this repo's
  `AGENTS.md`) are in every subagent's context, and they mention the Once UI harness.
  Every transcript is audited (`runner/audit-pilot.mjs`). Any read outside the arm's
  sandbox, or any command execution, voids the run, and the run is regenerated. The
  instructions themselves contain no Once UI API detail, but their presence is a
  threat to validity for arm B, noted in the pilot report.
- **Rating:** screenshots are blinded as in §4.5. The rater is a subagent that views
  the images.

## 8. Threats to validity

1. **Who built it.** The Once UI maintainers designed this benchmark. Mitigations:
   pre-registration, a task suite that predates the comparison, neutralised prompts, the
   competitor-favouring choices in §1.2, public raw outputs and scripts, and fixed
   claim rules.
2. **Task suite provenance.** The suite was written to exercise Once UI's inventory
   ("text effect", "background effect", "celebratory completion", "stacked dialog",
   "segmented control"). Stacks without those primitives have to hand-build them,
   which inflates their code. That is real cost, but the tasks weren't sampled from
   typical product UI. The sensitivity analysis (§5) and per-task tables expose this.
3. **Training-data asymmetry.** Tailwind and shadcn/ui are far more common in training
   data than Once UI. That favours C and D on correctness from memory (B vs D shows
   the size of the effect) and makes A's documentation reads necessary rather than
   optional.
4. **One model, small n.** Results hold for `claude-sonnet-5-5` at the settings above.
   n = 3 per cell gives medians with wide IQRs. Generalising to other models needs a
   replication.
5. **Placeholder content.** The amount of inline data (rows, FAQ items, tiers) varies by
   run and inflates every arm's code. Medians and n soften this but don't remove it.
6. **Static gates.** The render gate checks the initial state only. Dialogs, OTP steps,
   hover actions, sorting and toasts are not exercised, and screenshot rating can't see
   them. A page with a broken interaction can pass. (Pilot follow-up: scripted
   interaction checks per task, §10.)
7. **Docs representation.** C's docs are a local copy, without the rendered previews the
   website shows (the preview source is included instead). A's harness is exactly what
   ships in the package.
8. **Tooling shapes the result.** The repair loop feeds back compiler and runtime errors,
   which differ in helpfulness between stacks. That difference is part of what is
   measured.
9. **Version drift.** The 2.1 RC tarball may differ from the published 2.1.0. Re-run
   against npm (§10).
10. **Rater bias.** The model rater may prefer one visual style. Fonts and palettes can
    reveal the stack, so blinding is only partial.
11. **Pilot-specific.** Claude Code overhead in input tokens, unpinned thinking, and
    repository instructions in context (§7).
